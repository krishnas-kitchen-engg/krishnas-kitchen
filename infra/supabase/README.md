# Supabase

This directory contains the Supabase deployment assets for Krishna's Kitchen.

Do not commit secrets. Keep runtime values in `.env.local`.

## Structure

```text
infra/supabase/
  config.toml   # Supabase CLI local/staging configuration defaults
  migrations/  # SQL migrations generated by Supabase CLI
  policies/    # Row-level security policy drafts and reviewed SQL snippets
  schemas/     # Generated database type snapshots or schema references
  seed/        # Local-only seed data
  seed.sql      # Ordered validation seed entrypoint for Supabase CLI
  functions/   # Future Supabase Edge Functions
```

## Fresh Project Setup

Apply migrations in filename order from `migrations/`. For local Supabase CLI workflows, run commands from this directory or pass this directory as the Supabase workdir so `config.toml`, `migrations/`, and `seed.sql` are used together.

Default seed execution runs:

1. `seed/seed_validation_cleanup.sql`
2. `seed/seed_validation_core.sql`

Run `seed/seed_validation_expanded.sql` manually only when richer staging data is needed.

## Security Practices

- Enable row-level security on every table before it is used by the app.
- Write explicit policies for each role and operation. Avoid broad `using (true)` policies.
- Keep service-role keys out of browser code and out of `VITE_` variables.
- Treat anon-key access as public client access; authorization must live in RLS policies.
- Prefer SQL migrations for schema changes so policy and table history is reviewable.
- Generate database types after schema changes and commit the generated type snapshot.
- Store local credentials in `.env.local`; commit only `.env.example` files.

## RLS Preparation

Each migration that introduces protected database surface area should include table creation, indexes, grants, RLS enablement, and policy setup in the same reviewable change. Policy drafts can be staged in `policies/` before being promoted into a migration.

## Foundational Schema

The first migration is `migrations/20260525000100_foundational_schema.sql`.

It creates:

- `organizations`: tenant root with soft delete, status, slug, and metadata.
- `temples`: operating units scoped to an organization.
- `users`: application profiles linked to `auth.users` when a Supabase auth identity exists.
- `roles`: organization-level or temple-level role assignments.
- `locations`: storage hierarchy for kitchens, pantries, refrigerators, freezers, and other inventory areas.
- `items`: organization-owned inventory catalog.
- `item_barcodes`: one or more barcode aliases per item, with one optional primary barcode.
- `inventory_transactions`: immutable append-only inventory ledger.
- `volunteer_sessions`: minimal volunteer session scaffold.
- `audit_logs`: immutable audit event log.

All primary keys are UUIDs. Operational tables include `organization_id` for multi-tenancy. Mutable tables include `deleted_at` for soft-delete support. Immutable ledger/audit tables do not use soft delete.

## Assumptions

- A user profile belongs to one organization at this stage. Multi-organization identity support can be added later with membership tables if needed.
- `roles.temple_id` is nullable. A null value means the role applies across the organization.
- Inventory balance will be derived from `inventory_transactions`; no mutable stock balance table is created yet.
- Recipes, menu planning, procurement, suppliers, and feast planning are intentionally excluded.
- Supabase `auth.users` exists in the target project. The app profile can temporarily exist without `auth_user_id` for invited or manually entered volunteers.

## RLS Policy Direction

RLS is enabled on every foundational table, but policy definitions should be added once the first real access paths are known. Expected policy shape:

- Users can read their active organization profile and role assignments.
- `temple_admin` and `super_admin` users can manage temples, users, roles, locations, items, and barcodes within their allowed organization scope.
- Volunteers can read only the operational records needed for assigned temple workflows.
- Inventory transactions are insert-only for authorized roles and readable by authorized organization members.
- Audit logs are readable only by `temple_admin` and `super_admin` roles and writable only by trusted server-side code or controlled database functions.

## Future Extension Notes

- Add generated database types after running Supabase CLI against the schema.
- Add `updated_by` or `created_by` columns where audit requirements need explicit actor denormalization.
- Add inventory snapshot/materialized-view support if ledger-derived balance queries become hot.
- Add cross-organization memberships if the same auth identity must operate in multiple tenants.
- Add recipe, supplier, procurement, donation, and feast-preparation entities in later migrations.
